<objective>
Close the two `discord/panelkit.py` operator-gate footguns, both RED-first:

- **DISC-05 (H11, D-40):** `interaction_check` (`panelkit.py:299-331`) dereferences
  `interaction.user.bot` / `.id` with no guard (`:309`) → `AttributeError` when `interaction.user` is
  absent. Fix: a falsy guard at the TOP of the method — `if not interaction.user:` → emit the existing
  reject log (`panel reject (no user)`, custom_id only) and `return False`. No ephemeral ack (there is
  no user to ack). Keeps the gate's "a clean `return False` is the sole audit record" contract.
- **DISC-06 (H12, D-41):** `PanelKit.__init__` (`panelkit.py:157-192`) requires `marker` but never
  validates it; `cid.startswith("")` is always True, so `is_owned_panel` claims every bot-authored pin
  and `summon_panel` could delete unrelated pins. Fix: reject an empty / whitespace-only `marker` at
  construction (`raise ValueError`, right after `super().__init__(timeout=None)`, BEFORE the injected
  collaborators and `_build_children`/`_assert_layout`), matching the "no module default; fails LOUD at
  construction" idiom.

**Two verified RESEARCH corrections (bake in, cite so the executor doesn't write a wrong test):**
1. **DISC-05 is NOT an "escapes View.on_error" case.** RESEARCH.md §"Common Pitfalls #1" empirically
   proved (against real discord.py 2.7.1 `View._scheduled_task`) that an `AttributeError` inside
   `interaction_check` IS caught and routed to `on_error`. The D-40 fix is still exactly right (it
   restores the clean, silent, INFO-level reject-log contract instead of a noisy `on_error` backstop
   crash), but the RED test must call `interaction_check` **directly** and assert it returns `False`
   without raising — do NOT write a test asserting `on_error` was never invoked (it would be, and such
   a test would be wrong).
2. **The absent-user sentinel is `discord.utils.MISSING`, not `None`.** `Interaction.user` initializes
   to `MISSING` (a `_MissingSentinel`, `__bool__` → False, not `None`). The guard MUST be a **falsy
   check** (`if not interaction.user:`), not `is None`. A real `User`/`Member` is always truthy, so the
   falsy check cannot false-positive on a legitimate user (RESEARCH.md §"Common Pitfalls #1" bonus).
